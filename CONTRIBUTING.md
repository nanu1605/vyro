# Contributing to Clokrix

Thanks for helping. Clokrix is a Windows hardware monitor, and most of what it does can be built
and tested on any OS. Setup, layout and the check commands are in the
[README](README.md#development); what to build next is in [`ROADMAP.md`](ROADMAP.md).

## Before you open a pull request

Run what CI runs:

```sh
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo clippy -p clokrix-core --target x86_64-pc-windows-gnu --all-targets -- -D warnings  # Windows code, from Linux
cargo test -p clokrix-core                  # also regenerates src/bindings: commit any changes
cargo test -p clokrix-service
pnpm check && pnpm test && pnpm build
python3 scripts/bundle_budget.py --check # what each page loads at start, gzipped
pnpm a11y                                # axe-core on every tab, theme and width
python3 scripts/third_party.py --check   # after adding or updating a dependency
```

CI runs them on each push to a branch other than `main`, unless the push changes only the records
and docs (`ROADMAP.md`, `README.md`, `CONTRIBUTING.md`, `docs/` and the plans; no test reads
them), on pull requests, and by hand (Actions → CI → Run workflow). `main` is fast-forwarded only
to commits that passed on their branch, so CI does not run there again. The repository is
private, so each run spends the account's Actions allowance (about $0.35–0.40 a run in 2026-11).

`pnpm a11y` drives the browser preview with Playwright; install its browser once with
`pnpm exec playwright install chromium`. A change that stores something new in a state file
goes through `clokrix_core::files` (atomic writes, damaged files set aside). If it changes a
file's format, it gets a migration test with a file from the last release
(`crates/clokrix-core/tests/migration.rs`, `tests/fixtures/gen/`).

If you add or update a Rust crate or a UI package, run `python3 scripts/third_party.py` and
commit the regenerated `THIRD_PARTY_NOTICES.md` and `THIRD_PARTY_LICENSES.md`. Dependencies
must have licenses compatible with MIT OR Apache-2.0 distribution.

## How the code is organised

- **Decode apart from fetch.** Byte and register decoders (EDID, SMBIOS, SMART, SPD, Super-I/O,
  AMD SMN/MSR) are pure functions with fixture tests; a thin `#[cfg(windows)]` module reads the
  bytes. New hardware support should come with a fixture taken from a real machine.
- **Providers never break the tick.** A provider fills its slice of `SensorSnapshot` and the
  registry; anything it cannot read becomes `null` and is logged once.
- **The service is the only privileged process.** Anything that needs administrator rights
  (PawnIO, SMART, BitLocker) runs in the engine, which the service hosts; the app asks for it
  through `EngineApi` and must keep working, with less data, when the service is missing. A new
  engine call means a new `ipc::Request` variant; changing the shape of an existing message
  means bumping `ipc::PROTOCOL_VERSION`. The pipe is local only and never accepts file paths or
  anything that writes to hardware.
- **Rust is the source of truth for data types.** TypeScript types in `src/bindings/` are
  generated by ts-rs; never edit them by hand.

## Hardware access rules

Low-level reads go through the [PawnIO](https://github.com/namazso/PawnIO) driver with its
signed, unmodified modules (`crates/clokrix-core/pawnio/`, hashes checked by a test).

- **Read-only.** Clokrix never writes to Super-I/O, embedded-controller, SMBus or memory-controller
  registers beyond the index/bank selects a read needs. Fan control and other write paths are
  out of scope for v1.
- **Share the buses.** Take the global `Access_PCI`, `Access_ISABUS.HTP.Method` and
  `Access_SMBUS.HTP.Method` mutexes around the matching accesses (`pawnio::BusLock`), with a
  short timeout, so Clokrix coexists with HWiNFO, LibreHardwareMonitor and vendor tools.
- **No copied GPL code.** Register layouts may be learned from public documentation and other
  projects, but write the code yourself; say where a layout came from in a comment.

## Privacy

Serial numbers (board, drives, monitors, memory modules), MAC addresses, Wi-Fi SSID/BSSID and
global IPv6 addresses may be shown locally but are never logged, persisted, or sent anywhere.
Diagnostic dumps (`clokrix-live.json`, `clokrix-inventory.json`) leave them out or redact them by
default. Do not attach raw SPD EEPROM dumps to issues: they contain module serial numbers.

## Reporting hardware results

For a new CPU, board, GPU or memory kit, run `clokrix-live.exe` from a CI artifact (Actions → run
→ Artifacts) and attach `clokrix-live.json` together with an HWiNFO or HWMonitor report taken at
the same time. Say which readings look wrong.

## Releasing

Releases are built by `.github/workflows/release.yml`, never on a developer machine.

1. Once per repository: create the update signing key with `pnpm tauri signer generate -w
   clokrix-updater.key` (keep the file and password safe; losing them means installed copies can
   no longer update). In Settings → Secrets and variables → Actions, add the secrets
   `TAURI_SIGNING_PRIVATE_KEY` (the key file's contents) and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`,
   and the variable `UPDATER_PUBKEY` (the contents of `clokrix-updater.key.pub`).
2. Raise the version with `python3 scripts/set-version.py X.Y.Z` and commit (CI checks the
   manifests agree).
3. Run the Release workflow from the Actions tab on `main` (or push the tag `vX.Y.Z` on a
   commit of `main`). It builds the MSI with the updater enabled, signs it for the updater, and
   publishes release `vX.Y.Z` with the MSI, `latest.json` and `SHA256SUMS.txt`.

Branches: `main` is the released line (0.1.x fixes); V2 work happens on `v2` (feature branches
`v2-<phase>` merged into it) and is merged into `main` at each milestone, then released. The
workflow refuses other branches unless "prerelease" is ticked: that publishes a test build as
`vX.Y.Z-pre.N`, marked prerelease, which installed copies never update to.

Only these builds contain the updater; CI artifacts and local builds never check for updates.
Installed copies look for `latest.json` in the latest release. Release downloads of a private
repository need a sign-in, so while this repository is private the downloads go to a separate
public repository that holds no code: create it with a README, set the variable
`RELEASES_REPO` to its `owner/name`, and add the secret `RELEASES_TOKEN`, a fine-grained token
with Contents read and write on that repository only. The address is built into each release,
so copies installed before it was set keep looking in the old place until updated by hand.

### Downloads and updates from the website (2.5.2)

From 2.5.2 releases come from the company's own website, so both repositories can be private.
With the variable `CLOKRIX_SITE_HOST` set (the website's host, as for the checkout) and the
Cloudflare secrets, the Release workflow puts the MSI and `SHA256SUMS.txt` in the R2 bucket
`clokrix-downloads` under `vX.Y.Z/`, then `latest.json`, and builds the app to read
`https://<host>/updates/latest.json`. The checkout's Worker serves them
(`licence/src/downloads.ts`): `/download` is the newest installer, for the website's Download
button. Before the first release
of this kind, deploy the checkout once (Licence workflow): it makes the bucket. R2 has to be turned
on in the Cloudflare account first (dashboard → R2 Object Storage); its free allowance (10 GB
stored, downloads not charged) holds hundreds of releases.

`latest.json` names only the newest release, and each MSI is the whole of Clokrix with the same
upgrade code, so a copy several versions behind installs the newest in one step. What's new then
shows the notes of every version it skipped. CI's upgrade check installs Vyro 2.1.0 and upgrades
it straight to the build under test.

Making the repositories private, in this order:

1. Release 2.5.2 or later from the website, as above. `RELEASES_REPO` still gets each release:
   copies before 2.5.2 read it, and update from it to the newest.
2. Wait until installed copies have moved to 2.5.2 or later (they look daily). Any copy still
   older once the releases repository is private can no longer update itself; it needs the
   installer from the website's Download button, which keeps its settings.
3. Make `RELEASES_REPO` private (its Settings → General → Danger Zone → Change visibility). CI
   reads Vyro 2.1.0 from it with `RELEASES_TOKEN`.
4. Make this repository private the same way. Public forks stay public, and GitHub Actions minutes
   on a private repository count against the account's allowance (a Windows minute costs more
   than a Linux one). Free code signing (SignPath Foundation, decision 11) is for public open-source
   projects only.

Both were made private on 2026-11-20. `RELEASES_REPO` still gets each release, as a private copy
that no installed copy reads any more.
